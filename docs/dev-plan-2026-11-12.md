# Folio 개발 계획서 — 서버 전환과 Notion 90% (2026-11-12)

기준 문서: [parity-analysis-2026-11-12.md](parity-analysis-2026-11-12.md) (분류별 항목과 현재 점수). 이 계획서는 그 문서의 3절 P1(IndexedDB 이전), 6절(진행 순서), 7절(결정)을 대체합니다. 분류별 항목 목록(2절, 4절)은 그대로 씁니다.

출발점: 브랜치 `feature/notion-parity`, 1~4단계 완료, e2e 168개 통과, 브라우저 저장(localStorage) 전용.

## 2. 이 계획서에서 제가 정한 것 (검토 대상)

아래는 요청에 없던 부분을 제가 채운 것입니다. 바꾸고 싶은 항목만 알려주시면 됩니다.

| # | 항목 | 정한 내용 | 이유 |
|---|---|---|---|
| P-1 | 첫 관리자 보호 | 환경 변수 `ADMIN_EMAIL`에 적힌 이메일만 "첫 로그인"을 할 수 있음 | 외부에 공개된 서버라서, 주소를 먼저 알아낸 남이 첫 로그인을 하면 그 사람이 관리자가 됩니다 |
| P-2 | OTP 입력 시점 | 로그인할 때마다 입력. 로그인 유지 기간 14일 | 보안 강화가 목적이므로 "이 기기 기억" 옵션은 두지 않음 |
| P-3 | OTP 분실 | 등록 시 복구 코드 10개 발급. 관리자가 다른 사용자의 OTP를 초기화할 수 있음. 관리자 본인 분실은 NAS에서 명령으로 초기화 | 복구 수단이 없으면 계정이 영구히 잠깁니다 |
| P-4 | 서버 구성 | Node 22 + Fastify(웹 서버) + PostgreSQL 17 + ws(WebSocket) | 널리 쓰이고 DS920+에서 가볍게 돕니다 |
| P-5 | 화면 코드 | 지금의 순수 ES 모듈 방식을 유지. 외부 라이브러리만 esbuild로 묶어 `dist/vendor/`에 둠 | 전체를 프레임워크로 다시 쓰면 1~4단계 결과와 테스트를 버리게 됩니다 |
| P-6 | 동시 편집 방식 | 블록 단위 동기화. 서로 다른 블록을 고치면 둘 다 반영, 같은 블록을 동시에 고치면 글자 단위로 병합(Yjs 사용) | Notion도 블록 단위로 동기화합니다. 문서 전체를 글자 단위로 병합하는 방식보다 지금 편집기에 붙이기 쉽습니다 |
| P-7 | 오프라인 | 읽기와 편집을 브라우저에 임시 보관했다가 다시 연결되면 전송. 충돌은 P-6 규칙 | Notion의 오프라인 수준에 맞춤 |
| P-8 | 테스트용 로그인 | 테스트 실행 때만 켜지는 가짜 로그인 경로. `NODE_ENV=production`이면 서버가 시작을 거부 | Google 로그인 화면은 자동 테스트가 통과할 수 없습니다 |
| P-9 | 테스트용 DB | 이 PC에서는 PGlite(파일 하나로 도는 PostgreSQL 호환 DB), NAS에서는 실제 PostgreSQL | 개발 PC에 Docker가 없어도 테스트가 돕니다. 둘의 차이로 생기는 문제는 NAS 확인 단계에서 잡습니다 |
| P-10 | 권한 단계 | 워크스페이스: 소유자·관리자·멤버·게스트 / 페이지: 전체 권한·편집·댓글·보기 | Notion과 같은 구분 |
| P-11 | AI 연결 | 제공사를 바꿔 끼울 수 있는 구조. 어느 회사 키인지는 14단계 시작 전에 알려주시면 됨 | 키가 어느 회사 것인지 아직 모릅니다 |

## 3. 사용자께서 준비하실 것

| 언제까지 | 항목 | 설명 |
|---|---|---|
| 5단계 NAS 확인 전 | 도메인 | Synology DDNS(`이름.synology.me`) 또는 보유 도메인. Google 로그인은 IP 주소로는 등록할 수 없습니다 |
| 5단계 NAS 확인 전 | Google OAuth 클라이언트 | Google Cloud 콘솔에서 발급. 리디렉션 주소 `https://<도메인>/auth/google/callback` 등록. 클라이언트 ID와 비밀 키를 NAS의 환경 파일에 입력 |
| 5단계 NAS 확인 전 | 공유기 포트 포워딩 | 443 → NAS. DSM 관리 포트(5000/5001)는 열지 않음 |
| 5단계 NAS 확인 전 | 관리자 이메일 | `ADMIN_EMAIL`에 넣을 Google 계정 주소 |
| 9단계 전 (선택) | 메일 발송 계정(SMTP) | 초대·알림 메일용. 없으면 초대 링크를 직접 전달하고 알림은 앱 안에서만 표시 |
| 14단계 전 | AI 제공사와 모델 이름 | 키 자체는 NAS 환경 파일에만 넣으시면 됩니다. 저에게 알려주실 필요 없습니다 |

비밀 값(OAuth 비밀 키, AI 키, 세션 암호화 키)은 저장소에 커밋하지 않습니다. `.env.example`에 이름만 적어 둡니다.

## 4. 구조

```
브라우저 ──HTTPS──> DSM 리버스 프록시(인증서, WebSocket 허용)
                         │
                         ▼
               [컨테이너] folio-app  (Node 22, 포트 4317)
                 ├ 화면 파일 제공 (dist/)
                 ├ /auth/*   Google 로그인, OTP, 세션
                 ├ /api/*    페이지·블록·데이터베이스·파일·검색·AI
                 └ /ws       실시간 편집, 접속자 표시, 알림
                         │
            ┌────────────┴────────────┐
            ▼                         ▼
 [컨테이너] folio-db            NAS 공유 폴더 (볼륨)
   PostgreSQL 17                 /data/files  첨부 파일
   (볼륨: /data/postgres)        /data/backup DB 덤프
```

### 저장 구조 (주요 테이블)

| 묶음 | 테이블 | 내용 |
|---|---|---|
| 계정 | `users`, `sessions`, `invites`, `otp_secrets`, `recovery_codes`, `audit_log` | OTP 비밀 값은 암호화해 저장, 복구 코드는 해시만 저장 |
| 공간 | `workspaces`, `workspace_members`, `teamspaces` | 역할 포함 |
| 문서 | `pages`, `blocks`, `page_versions` | 블록은 `parent_id`와 순서 값을 가진 트리. 버전마다 작성자 기록 |
| 데이터베이스 | `databases`, `db_properties`, `db_rows`, `db_views` | 행은 페이지와 연결 (D4 유지) |
| 권한 | `page_permissions`, `public_links` | 상위 페이지 권한을 물려받고 페이지별로 덮어씀 |
| 협업 | `comments`, `notifications`, `page_views` | |
| 파일 | `files` | 실제 파일은 볼륨, 표에는 이름·크기·종류·올린 사람 |
| 연동 | `api_tokens`, `webhooks` | |

### 보안 기준 (모든 단계 공통)

- 세션 쿠키: `HttpOnly`, `Secure`, `SameSite=Lax`. 상태를 바꾸는 요청은 CSRF 토큰 검사.
- 모든 `/api`, `/ws` 요청은 "로그인됨 + OTP 통과 + 해당 페이지 권한 있음"을 서버에서 검사. 화면에서 버튼을 숨기는 것은 보안이 아닙니다.
- 로그인·OTP 시도 횟수 제한(5회 실패 시 15분 잠금), 관리 작업은 `audit_log`에 기록.
- 업로드: 크기 제한(기본 50MB), 종류 검사, 내려받기 전용 헤더로 제공해 올린 HTML·SVG가 사이트 안에서 실행되지 않게 함.
- 임베드: 허용 사이트 목록 + iframe sandbox. 콘텐츠 보안 정책(CSP) 헤더 적용.
- AI 키와 OAuth 비밀 키는 서버에만 있고 브라우저 응답에 포함하지 않음.

## 5. 단계별 계획

크기는 1~4단계 중 한 단계를 1로 본 상대값이며 기간 약속이 아닙니다. "올라가는 분류"의 수치는 분석 문서의 항목 수로 계산한 예상값입니다.

### 5단계 — 서버 기반과 로그인 (크기 2)

- 저장소 구조: `server/`(서버 코드), `dist/`(화면, 유지), `deploy/`(Compose 파일, `.env.example`, NAS 설치 안내).
- PostgreSQL 연결, 스키마 버전 관리(마이그레이션 파일), PGlite 테스트 환경.
- Google 로그인(OpenID Connect), 초대 이메일 확인, 첫 관리자(P-1).
- OTP 등록(QR 코드), 로그인 시 검증, 복구 코드, 관리자 초기화.
- 관리자 화면: 초대 보내기·취소, 사용자 목록, 역할 변경, 사용 중지, 감사 기록.
- 4절 보안 기준 적용.
- **NAS 확인**: 이 단계 끝에 실제 DS920+에 올려 Google 로그인과 OTP가 도는지 사용자와 함께 확인. 여기서 막히면 뒤 단계가 모두 영향을 받으므로 가장 먼저 검증합니다.
- 완료 기준: 초대받지 않은 계정은 거부, OTP 미등록 사용자는 등록 화면만 보임, 로그인 없이 `/api` 호출 시 401.

### 6단계 — 저장을 서버로 전환 (크기 2.5)

- 페이지·블록·데이터베이스·워크스페이스 API. 화면의 `store.js`를 "서버와 주고받는 저장 계층"으로 교체.
- 블록을 트리 구조로 변경(분석 문서 P2). 서버 저장 형식을 새로 만드는 지금이 바꾸기에 가장 싼 시점입니다.
- 페이지 주소(`/p/<id>`), 뒤로·앞으로, 링크 복사(분석 문서 P4).
- 기존 브라우저 데이터 옮기기: JSON 백업 파일을 서버에 올리면 내 워크스페이스로 들어옴. 페이지 기록도 서버로 이전.
- 파일 올리기·내려받기 API와 볼륨 저장.
- `app.js`를 기능별 파일로 분할.
- 기존 e2e 168개를 서버 환경에서 다시 통과시킴. 이 단계에서 가장 많은 테스트를 손봅니다.
- 올라가는 분류: J 9→45%, D 71→83%, F 69→77%.

### 7단계 — 권한과 공유 (크기 1.5)

- 워크스페이스 역할, 페이지별 공유(사람 지정, 권한 수준), 상속, 게스트.
- 팀스페이스, 사이드바의 "개인 페이지 / 공유됨 / 팀스페이스" 구획.
- 웹 게시: 로그인 없이 볼 수 있는 읽기 전용 공개 링크(끄기 가능, 검색 엔진 차단 기본).
- 페이지 잠금, 데이터베이스 잠금.
- 완료 기준: 권한 조합별 API 테스트(보기 권한자가 수정 요청 시 403 등).
- 올라가는 분류: H 0→42%.

### 8단계 — 실시간 동시 편집 (크기 2.5)

- WebSocket 연결, 접속자 표시(아바타, 다른 사람의 커서 위치).
- 블록 단위 변경 전파와 병합(P-6), 끊겼다 다시 붙을 때 밀린 변경 전송.
- 오프라인 임시 보관과 재전송(P-7).
- 실행 취소는 "내가 한 변경만" 되돌리도록 수정.
- 완료 기준: 브라우저 두 개로 같은 페이지를 동시에 고치는 e2e. 같은 블록 동시 편집, 한쪽 오프라인 후 복귀 포함.
- 이 계획에서 기술적으로 가장 어려운 단계입니다.
- 올라가는 분류: H 42→50%, J 45→55%.

### 9단계 — 댓글·멘션·알림 (크기 1.5)

- 페이지 댓글과 텍스트 선택 댓글, 답글, 해결 처리.
- 서식 모델에 인라인 요소 추가(분석 문서 P3): 사람 멘션, 페이지 멘션, 날짜 멘션·리마인더.
- 알림함, 메일 알림(SMTP가 있을 때), 페이지 팔로우.
- 편집자별 변경 기록, 페이지 조회 기록, 제안 모드(변경을 제안으로 남기고 승인·거절).
- 올라가는 분류: H 50→92%, B 62→85%.

### 10단계 — 편집 조작과 블록 확장 (크기 2.5)

- 여러 블록 선택과 일괄 처리, 블록 색상, 이동·전환 단축키, 블록 링크.
- 이미지·동영상·오디오·파일·PDF 블록, 끌어다 놓기·붙여넣기, 아이콘·커버 이미지 올리기.
- 컬럼, 단순 표, 토글 제목, 동기화 블록, 이동 경로 블록, 버튼 블록.
- 수식(KaTeX), 코드 언어 선택과 구문 강조, Mermaid, 인라인 수식.
- 북마크(서버가 대상 사이트의 제목·이미지를 가져옴. 서버가 생겼으므로 완전 구현 가능), 임베드.
- 글꼴 3종, 단어 수.
- 올라가는 분류: A 44→88%, B 85→92%, C 60→95%, D 83→96%.

### 11단계 — 데이터베이스 속성 (크기 2)

- 상태, 이메일, 전화, 파일, 생성·편집 일시, 고유 ID, 버튼.
- 사람, 생성자, 최종 편집자 (계정이 생겼으므로 구현 가능).
- 관계형(양방향), 롤업, 수식(식 해석기와 함수 목록).
- 숫자 형식, 날짜 범위·시간.
- 올라가는 분류: E 43→73%.

### 12단계 — 데이터베이스 보기와 기능 (크기 2)

- 타임라인, 차트, 양식(입력 폼) 보기.
- 인라인 데이터베이스, 연결된 보기.
- 필터 그룹(AND/OR), 표·목록 그룹화, 열 너비·줄바꿈, 행 템플릿, 하위 항목·종속성, CSV 병합.
- 자동화: 조건→동작. 서버에서 돌기 때문에 앱을 닫아도 동작.
- 올라가는 분류: E 73→96%, A 88→94%.

### 13단계 — 검색과 가져오기·내보내기 (크기 1)

- 서버 전문 검색(권한이 있는 페이지만 결과에 나옴), 검색 필터, 미리보기·강조, 최근 검색어.
- 하위 페이지 포함·워크스페이스 전체 내보내기(zip), PDF 내보내기.
- HTML·Word·Notion 내보내기 zip 가져오기.
- 올라가는 분류: F 77→100%, G 57→93%.

### 14단계 — AI (크기 1.5)

- 제공사 연결 계층(P-11), 사용량 기록, 사용자별 한도.
- 글쓰기 도우미(이어 쓰기, 다듬기, 길이 조절), 요약, 번역.
- 워크스페이스 질의응답: 질문한 사람이 볼 수 있는 페이지만 근거로 사용.
- 데이터베이스 자동 채우기(요약·분류 속성).
- 회의록: 녹음 파일을 올리면 정리. 음성 인식이 되는 API여야 하며, 안 되면 텍스트 붙여넣기 정리까지만 구현.
- 올라가는 분류: I 0→92% (회의록이 일부 구현에 그치면 92%, 완전 구현이면 100%).

### 15단계 — 플랫폼 (크기 1.5)

- 설치형 웹앱(PWA): 홈 화면·바탕화면에 설치, 오프라인 실행.
- 공개 API(토큰 발급, 페이지·데이터베이스 읽기·쓰기), 웹훅.
- 웹 클리퍼(브라우저 확장 프로그램).
- 올라가는 분류: J 55→82%.

### 16단계 — 디자인 대조와 마무리 (크기 1.5)

- Notion 화면을 기준으로 화면별 대조표를 만들고 색·글자 크기·여백·아이콘을 맞춤. 로고와 문구는 Folio 것을 유지.
- 드래그 안내선, 메뉴 키보드 탐색, 전환 효과, 모바일 편집 도구 막대, 다크 테마 전 화면 점검.
- Firefox·Safari 확인.

### 17단계 — 운영 (크기 1)

- 매일 DB 덤프와 보관 주기, Hyper Backup 연동 안내, 복원 연습 1회.
- 서버 상태 확인 주소, 오류 기록, 디스크 사용량 경고.
- 업데이트 절차(이미지 교체, 스키마 변경 자동 적용, 되돌리기 방법).
- 부하 확인: 동시 접속 20명 기준.

**합계 크기 약 28.** 1~4단계 전체(4)의 약 7배입니다.

## 6. 단계가 끝났을 때 예상 일치도

| 분류 | 현재 | 완료 후 예상 | 90% 달성 |
|---|---|---|---|
| A 블록 | 44% | 94% | 예 |
| B 서식 | 62% | 92% | 예 |
| C 편집 조작 | 60% | 95% | 예 |
| D 페이지 관리 | 71% | 96% | 예 |
| E 데이터베이스 | 43% | 96% | 예 |
| F 검색 | 69% | 100% | 예 |
| G 가져오기·내보내기 | 57% | 93% | 예 |
| H 협업 | 0% | 92% | 예 |
| I AI | 0% | 92~100% | 예 |
| J 계정·플랫폼 | 9% | 82% | **아니오** |

**J는 이 계획으로 90%에 닿지 않습니다.** 남는 항목은 데스크톱 전용 앱, 모바일 전용 앱, 외부 서비스 연동(Slack·GitHub 등)입니다. 설치형 웹앱과 웹훅으로 각각 절반씩만 인정했습니다. 90%를 채우려면 앱 스토어 배포용 모바일 앱이나 데스크톱 앱을 따로 만들어야 하는데, 별도 프로젝트 규모이고 앱 스토어 개발자 계정도 필요합니다. 포함할지는 15단계 전에 정하시면 됩니다.

수치는 분석 문서와 같은 방식(항목 수 세기)의 예상값이고, Notion 쪽 항목은 실제 화면과 대조한 것이 아닙니다.

## 8. 공통 규칙

- 단계마다: 구현 → `npm run check` → e2e 전체 통과 → README 갱신 → 로컬 커밋 → 결과 보고(계획과 달라진 점, 확인하지 못한 것 포함).
- 삭제 명령을 쓰지 않습니다. 파일을 없애야 하면 옮기거나 먼저 묻습니다.
- NAS에 올리는 작업은 사용자가 직접 하거나 요청하실 때만 합니다. 안내 문서는 `deploy/`에 둡니다.
- 서버 스키마를 바꿀 때는 항상 마이그레이션 파일로 하고, 적용 전 자동 덤프를 남깁니다.

## 9. 시작 전 확인

5단계는 준비물 없이 이 PC에서 바로 시작할 수 있습니다(테스트용 로그인과 PGlite 사용). 3절의 도메인과 Google OAuth 클라이언트는 5단계 끝의 NAS 확인 때 필요합니다.
