# Notion 대비 일치도 분석과 90% 달성 조건 (2026-11-12)

대상: `feature/notion-parity` 브랜치, 커밋 `1f4eae0` (1~4단계 완료, e2e 168개 통과).

## 0. 이 문서를 읽는 법

- **세는 방법**: 분류마다 Notion 기능을 항목으로 나열하고, Folio에 있으면 1점, 일부만 있으면 0.5점, 없으면 0점으로 셌습니다. 일치도 = 점수 ÷ 항목 수. 항목마다 무게는 같습니다.
- **근거**: Folio 쪽은 코드(`dist/*.js`)를 직접 확인했습니다. Notion 쪽 항목은 제가 알고 있는 Notion 기능 목록이며, 이번에 실제 Notion 화면과 대조해 확인한 것은 아닙니다. Notion은 계속 바뀌므로 항목 수는 ±몇 개 달라질 수 있습니다.
- **어제 수치와의 차이**: 어제 답변은 대략적인 추정이었습니다. 항목을 하나씩 세어 보니 서식(75%→62%)과 데이터베이스(55%→43%)는 어제보다 낮게 나왔습니다. 이 문서의 수치가 기준입니다.
- **결론 먼저**: 분류 10개 중 7개는 지금 구조(브라우저 전용)를 확장해서 90%에 도달할 수 있습니다. 나머지 3개(협업, 계정·동기화, AI)는 서버·계정·외부 AI API가 있어야 하며, 지금까지의 결정 D5(제외)를 뒤집어야 합니다. 이 3개는 앞의 7개를 전부 합친 것보다 큰 작업입니다.

## 3. 선행 작업 (기능보다 먼저 바꿔야 하는 구조)

| # | 작업 | 왜 필요한가 | 영향 |
|---|---|---|---|
| P1 | 저장소를 IndexedDB로 이전 + 파일 저장소 | localStorage는 약 5MB라 이미지·파일을 못 담음 | 저장·불러오기 전체, 백업 형식(파일 포함 zip), 다른 탭 보호 방식, 저장 버전 5 |
| P2 | 블록을 트리 구조로 | 지금은 평평한 배열 + 들여쓰기 숫자. 컬럼·표·동기화 블록·인라인 데이터베이스는 "블록 안의 블록"이 필요 | 편집기 전체, 실행 취소, Markdown 변환, 기존 테스트 다수 |
| P3 | 서식 모델에 인라인 요소 추가 | 멘션·인라인 수식은 글자가 아닌 "한 덩어리" | `richtext.js`, 커서 이동, 붙여넣기 |

| P6 | 수식 계산기 | 데이터베이스 수식 속성 | 새 모듈 |
| P7 | 서버·계정 | H, J 전체와 사람 관련 항목 | 4절 참고 |

추가로 `app.js`가 1,046줄(줄당 수백 자)이라 위 작업 전에 파일을 기능별로 나누는 정리가 필요합니다.

**위험이 가장 큰 것은 P1과 P2**입니다. 둘 다 저장 형식을 바꾸고 기존 e2e 168개 중 상당수를 손봐야 합니다.

## 4. 서버가 필요한 분류 (H, I, J)

### H. 협업·공유·권한 — 0% (0/12)

페이지 공유 초대, 권한 수준(전체·편집·댓글·보기), 댓글 대화, 멘션 알림, 실시간 동시 편집, 팀스페이스, 웹 게시, 게스트, 알림함, 편집자별 변경 기록, 페이지 분석(조회 수), 제안 모드.

필요한 것: 계정·인증, 서버 데이터베이스, 권한 검사, 실시간 통신과 충돌 해결(CRDT 등), 알림 발송, 공개 페이지 렌더링, 운영 환경.

### I. AI — 0% (0/6)

글쓰기 도우미, 요약, 번역, 워크스페이스 질의응답, 데이터베이스 자동 채우기, 회의록.

필요한 것: 외부 AI API와 키(사용량만큼 비용 발생), 키를 숨기기 위한 서버 경유, 질의응답용 색인.

### J. 계정·동기화·플랫폼 — 9% (1/11)

있는 것: 브라우저 내 워크스페이스 여러 개(✅), 배포 환경의 로그인 화면(계정별 저장소가 아니므로 0점 처리).
없는 것: 계정별 데이터, 서버 동기화, 여러 기기, 오프라인 후 동기화, 데스크톱 앱, 모바일 앱, 공개 API, 외부 연동, 웹 클리퍼, 설치형 앱(PWA).

서버 없이 가능한 것은 PWA 하나뿐입니다(→18%).

### 이 세 분류에 대한 솔직한 평가

- A~G 전체보다 큰 작업입니다. Notion이 여러 해에 걸쳐 만든 부분이고, 만든 뒤에도 서버 운영·비용·보안 책임이 계속 따릅니다.
- "브라우저에만 저장하는 개인용 앱"이라는 지금의 전제(README, 결정 D5)를 버려야 합니다. 저장 방식이 서버 중심으로 바뀌면 A~G에서 만든 저장 코드도 다시 손봐야 하므로, **할 거라면 P1 전에 결정**하는 것이 낫습니다.
- 데스크톱·모바일 앱과 공개 API·연동까지 90%를 채우는 것은 이 저장소 범위를 넘어섭니다.
